**Findings**
1. High: `schema_version` を v1 に据え置く判断は、ADR-015 の version gate 契約と衝突しています。[draft §3-4]([017-phase10-sketch-curves-and-edits.md](/home/bacon/engawacad/docs/decisions/017-phase10-sketch-curves-and-edits.md:81)) では `SketchTrim` など新しい `Feature.type` と新しい `SketchElement.kind` を追加しつつ、[§4]([017-phase10-sketch-curves-and-edits.md](/home/bacon/engawacad/docs/decisions/017-phase10-sketch-curves-and-edits.md:129)) で migration 不要・`schema_version` 据え置きを宣言しています。しかし ADR-015 は `schema_version` を format 進化の入口として置き、[Document::from_yaml]([document.rs](/home/bacon/engawacad/crates/engawa-format/src/document.rs:73)) は stage 1 で future schema を弾く設計です。実際に [受け入れテスト]([schema_version_migration_acceptance.rs](/home/bacon/engawacad/crates/engawa-format/tests/schema_version_migration_acceptance.rs:100)) も「未知の future feature は `UnknownSchemaVersion` で止める」ことを契約化しています。新 wire shape を v1 に紛れ込ませると、旧 reader では「未来フォーマット」ではなく「壊れた v1」として深い serde error になり、ADR-015 の互換方針を壊します。

2. High: `sketch_ref: EntityRef` は型の意味域を越えており、ADR-005 の層分離を壊しています。[draft §3]([017-phase10-sketch-curves-and-edits.md](/home/bacon/engawacad/docs/decisions/017-phase10-sketch-curves-and-edits.md:83)) は sketch 編集 op の参照先に `EntityRef` を使いますが、現行 `EntityRef` は [Face/Edge/Vertex 専用]([feature.rs](/home/bacon/engawacad/crates/engawa-format/src/feature.rs:7)) の topological naming 型です。ADR-005 でも Feature 間参照はまず `feature_id` を anchor にし、`EntityRef` は B-rep entity の安定参照として導入されています([ADR-005](/home/bacon/engawacad/docs/decisions/005-topological-naming.md:28))。現在の `Extrude` も sketch 参照は単なる `String` です([feature.rs](/home/bacon/engawacad/crates/engawa-format/src/feature.rs:423))。ここを `EntityRef` に寄せると、「sketch 履歴を編集するために build 後 topology naming が要る」逆転が起き、Phase 10 の sketch 層が Phase 4/5 の B-rep 参照層へ不要に依存します。

3. High: `Rectangle / Polygon / Slot` を単一 `SketchElement` として保持する案は、ADR-005 の stable naming 契約を未解決のまま破ります。[ADR-005]([005-topological-naming.md](/home/bacon/engawacad/docs/decisions/005-topological-naming.md:163)) は Extrude 側面 role を `side_<sketch要素安定名>` としており、sketch element id は安定 seed です([005-topological-naming.md](/home/bacon/engawacad/docs/decisions/005-topological-naming.md:184))。一方 [draft §1]([017-phase10-sketch-curves-and-edits.md](/home/bacon/engawacad/docs/decisions/017-phase10-sketch-curves-and-edits.md:43)) は Rectangle/Polygon/Slot を 1 要素として保存し、後段で Line/Arc に分解する前提です。これでは 1 要素から複数 boundary edge・複数 side face が生まれるのに、どの canonical role をどう振るかが未定義です。さらに [§3 の `{a}_split_{n}`]([017-phase10-sketch-curves-and-edits.md](/home/bacon/engawacad/docs/decisions/017-phase10-sketch-curves-and-edits.md:93)) は生成順カウンタ系の命名で、ADR-005 が禁じる「列挙順依存の stable name」に近く、trim 順や再編集順で identity が揺れます。

4. Medium: `Conic { coeffs: [f64; 5] }` を「`F = -1` で正規化」とする表現は、そもそも全 conic を表せません。[draft §1]([017-phase10-sketch-curves-and-edits.md](/home/bacon/engawacad/docs/decisions/017-phase10-sketch-curves-and-edits.md:49)) は 5 自由度化のために定数項固定を選んでいますが、`F = 0` の conic はこの正規化に乗りません。典型例は原点を通る放物線 `y = x^2` です。つまり採用した serialized model 自体が advertised domain の全域を覆っておらず、Phase 10 の時点で再設計トリガを内包しています。

5. Medium: 退化閾値の置き場も ADR-004 と噛み合っていません。[draft §2]([017-phase10-sketch-curves-and-edits.md](/home/bacon/engawacad/docs/decisions/017-phase10-sketch-curves-and-edits.md:62)) は `EPS_LENGTH`/`EPS_ANGLE` と新規 ε を `geometry/tolerances.rs` に寄せますが、ADR-004 の公開契約は [ `geometry::math` の `LENGTH_TOLERANCE` / `ANGLE_TOLERANCE` / `RELATIVE_TOLERANCE` ]([004-freeform-geometry-commitment.md](/home/bacon/engawacad/docs/decisions/004-freeform-geometry-commitment.md:46)) と、Phase 4 以降の [ `geometry::tolerance::Tolerance` ]([004-freeform-geometry-commitment.md](/home/bacon/engawacad/docs/decisions/004-freeform-geometry-commitment.md:80)) です。sketch authoring 上の退化 policy を kernel 全体の tolerance 契約へ直結させると、B-rep 幾何の比較公差と sketch 編集 UX の閾値が同一モジュールで結合し、後で片方だけ調整しづらくなります。

この draft は個別の API 名や ε 値の問題ではなく、永続フォーマットの進化境界、`EntityRef` の適用域、sketch element id を種にした stable naming、そして conic 表現の全域性が同時に崩れています。特に `schema_version` 据え置きのまま新 `Feature.type` / `SketchElement.kind` を追加する点は ADR-015 の 2 段階 version gate を正面から破り、`Rectangle/Polygon/Slot` と `{a}_split_{n}` は ADR-005 の「順序非依存・seed 安定」原則を満たしていません。Phase 10 の局所最適で format/build/kernel の層境界をまたいでしまっており、このまま accept すると Phase 11 以降で互換性と naming の再設計がほぼ確実です。
verdict: refuted
