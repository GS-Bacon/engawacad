refute理由: ADR-015 は設計基盤 ADR として不安定です。第1に、採用案は「engawa-build の CRUD 抽象」と言いながら `Document::apply_op(op: FeatureOp) -> Result<(), BuildError>` を掲げており、`Document` を持つ format 層 (`engawa-format`) に build 層の `BuildError` と mutation policy を逆流させます。現行の crate 依存は `engawa-build -> engawa-format` であり、この API は循環依存か `Document` 所有権の移動を要求し、ADR-007/014 までで保ってきた format/build 分離を壊します。しかも実装はすでに `FeatureCrud::{insert,edit,...}` の root-centric 個別 API で成立しており、ADR の中心抽象自体が安定境界として機能していません。第2に、`Edit { mutate: Box<dyn FnOnce(&mut Feature)> }` は非 serialize・非 inspectable で、ADR 自身が棄却理由に挙げた trait object の欠点を Option B 側で再導入しています。これでは「CLI verb と 1:1」「Undo/Redo は `inverse()` で統一」の根拠が立ちません。`Delete`/`RollBack`/`Edit` の inverse には旧 feature 状態や切り落とした履歴の payload が必要ですが、その契約が仕様化されていないため、採用理由の中核が未成立です。第3に、Variable 節は「Component を越えないので ADR-007 と直交」と述べますが、`Document` scope は component 階層の外側にあるため実際には全 component への ambient scope です。`Component` が feature を持てる以上、child/stdlib 側の sketch も親 document 変数に暗黙依存し得ます。さらに `${name}` 単一構文＋shadowing だけでは、Sketch 側で同名を置いた瞬間に outer `Document` 変数を明示参照する手段が消え、ADR-014 の独立性と再利用性を弱めます。MigrationHook も driver を後回しにしつつ hook 自己同定手段を持たず、foundation と呼ぶには契約が薄すぎます。
verdict: refuted
