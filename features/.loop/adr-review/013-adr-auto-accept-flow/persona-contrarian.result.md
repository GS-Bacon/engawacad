1. `Multi-LLM Adversarial Review` は、この ADR が自分で問題視している「Codex draft 単独では reviewable でない」を解決していません。GLM 3 ペルソナは見かけ上は多重防御でも、同系統モデル・同一入力・同一評価軸に強く相関するため、最も危険な「3者そろって誤って approved」を検出できません。しかも trigger は「同じ refute 理由が続くこと」しか見ておらず、相関した誤承認には無力です。

2. `cap` と token 試算が自己矛盾しています。記載どおりなら初回だけで `draft 30k + review 3×30k = 120k` です。1 回でも再生成して再レビューすれば 240k に達し、`1 ADR あたり token 上限 = 200k` を即座に超えます。なのに同じ文書で「再生成平均 2 回」「ADR 1 件 ~150k token」としており、運用像が両立していません。この設計だと first-pass 以外の ADR はほぼ `needs-human` 退避になり、Phase 8-20 無人方針と正面衝突します。

3. `needs-human を付けて loop 全体は止めず次 Issue へ進む` は、ADR の役割と衝突します。ADR は下流実装の前提を固定するためのものなのに、未解決のまま batch-select が先へ進むと、却って本文が懸念している「誤判定の後 Phase 伝播」を制度的に増やします。却下した現状維持案 `(a)` は、少なくともこの依存関係を明示的にブロックでき、アーキテクチャ上は一貫しています。

4. 既知 race を認めている箇所に、さらに `3 ペルソナ並列実行`、`regen_count 永続化`、`gate 削除/close`、`監査 Issue 自動起票` を足していますが、版管理・idempotency・stale review 排除の記述がありません。古い draft に対する review 結果で新しい draft を close する、再試行で counter を二重加算する、といった失敗モードが見えています。現状維持案 `(a)` の利点は、品質だけでなく状態機械が単純で壊れ方が読みやすい点にもあります。

5. `(a) 現状維持` を「数ヶ月レベルで遅延」と切って捨てていますが、根拠がありません。10-12 件の ADR に対し、日次または Phase 境界でまとめて人間判定する運用でも、真のモード多様性と明示的ブロックを保ったまま遅延をかなり抑えられます。採用案は“完全自律”を守るために見えて、実際には `needs-human` と事後監査を持ち込んでおり、むしろ中途半端です。

refute 理由: 本 ADR は「pause を外しつつ品質を守る」と言いながら、中心防御である Multi-LLM review が独立した審査になっておらず、最重要の失敗モードである相関した誤承認を防げていません。加えて token 設計は数式レベルで破綻しており、初回 fail 後に 200k cap を超えやすいため、`needs-human` が例外ではなく常態化する構造です。そのうえ `needs-human` 退避後も下流 Issue を進めるため、ADR 未確定のまま実装が進むという本末転倒を招きます。既知 race を抱える箇所へ非同期状態遷移を増やしているのに整合性制御も未定義です。却下された現状維持案は、少なくとも真の審査多様性、依存関係の明示的ブロック、単純な失敗モードを持っており、この草案よりアーキテクチャ的に健全です。したがって採用案は refute 可能です。
verdict: refuted
